# HTTP 状态码（FastAPI 里高频用的）

一句话先记住：**状态码是服务器返回给前端 / 调用方的简短信号，告诉对方这次请求 “结果怎么样”**，FastAPI 可以直接在路由里指定返回码，也会自动返回一部分。

## ✅ 2xx 成功类（请求正常搞定）

2. **200 OK**
- 含义：请求成功，服务器正常返回数据（最常用）
- 什么时候用：查询数据、正常接口返回结果，**默认就是 200**
- FastAPI 示例：直接 return 数据，默认 200

```
@app.get("/user")
def get_user():
    return {"name":"songyj"} # 默认200
```

3. **201 Created**
- 含义：**新建资源成功**（创建了一条数据）
- 什么时候用：新增用户、新增订单、POST 提交创建数据
- FastAPI 写法：`status_code=201`

```
@app.post("/user", status_code=201)
def create_user():
    return {"msg":"创建成功"}
```

4. **204 No Content（你问的 204）**
- 含义：**成功，但是没有返回任何响应体**
- 什么时候用：删除操作、部分更新，不需要返回内容

> 重点坑：204 不能带返回 json！很多新手踩错，写了 return 内容浏览器收不到

```
@app.delete("/user/{uid}", status_code=204)
def del_user(uid:int):
    # 删除逻辑，不要return json
    return None
```

## ⚠️ 4xx 客户端错误（是调用方的问题）

2. **400 Bad Request**
- 含义：**请求参数错了**，服务器看不懂你的请求
- 什么时候用：参数格式不对、传的字段非法、参数校验失败

> FastAPI 自动校验 Pydantic 模型失败时，默认返回 422，不是 400；你主动判断业务错误时手动抛 400

```
from fastapi import HTTPException
if age < 0:
    raise HTTPException(status_code=400, detail="年龄不能是负数")
```

3. **401 Unauthorized**
- 含义：**未登录 / 身份凭证无效**（没有 token、token 过期）

> 区分：401 = 你没资格证明自己是谁

4. **403 Forbidden**
- 含义：**登录了，但是权限不够**（身份合法，但是不让操作）

> 区分口诀：401 = 没登录；403 = 登录了，但不让干

5. **404 Not Found**
- 含义：资源不存在
- 什么时候用：查 id=100 的用户，库里没有这个用户；访问不存在路由
  FastAPI 路由不存在自动返回 404
6. **422 Unprocessable Entity**
- 含义：格式收到了，但是校验不通过（Pydantic 类型校验失败默认返回这个！）
  比如你传字符串给 int 类型参数，FastAPI 自动 422，这个在 FastAPI 里超级高频

## ❌ 5xx 服务端错误（服务器自己炸了）

2. **500 Internal Server Error**
- 含义：服务器内部异常，代码报错、数据库崩了
- 原则：**尽量不要手动抛 500，代码异常 FastAPI 自动返回**，业务错误优先用 4xx



# 📌 快速记忆口诀（写接口直接对照）

- 200：正常查数据，返回结果
- 201：POST 新建资源成功
- 204：删除 / 清空，成功、不返回内容
- 400：参数业务非法（比如负数、非法值）
- 401：没登录 /token 失效
- 403：登录了，权限不足
- 404：资源找不到
- 422：参数类型校验失败（FastAPI 标配）
- 500：服务器代码出错

# 📌 补充一个 FastAPI 最佳实践

- 查询 GET → 200
- 创建 POST → 201
- 修改 PUT/PATCH → 200
- 删除 DELETE → 204
- 参数校验失败 → 优先 422（框架自动），业务逻辑错误（比如余额不足）→ 400





## 第 3 条 · 查询用户详情

- 方法：`GET`
- 路径：`/api/users/{id}`
- 入参（path）：`id` int 必填，填在 URL 里
- 出参（data）：`id` int；`name` string；`age` int
- 状态码：成功 `200`；找不到 `404`

```json
{
  "code": 200,
  "msg": "success",
  "data": { "id": 3, "name": "Rookie", "age": 20 }
}
```

**为什么这么写（你要能自己说出来）：**

| 字段                | 为什么                                                |
| ----------------- | -------------------------------------------------- |
| `GET`             | 查询不改数据，只读，所以用 GET                                  |
| `/api/users/{id}` | `{id}` 是"某一条"的占位符，不是 `/getUser` ——路径里只放名词，动作用方法表达  |
| 入参在 path          | 你要"哪一条"用户，这个 id 本身就是定位资源的一部分，所以属于路径，不是 query       |
| 出参只有 3 个字段        | 返回前端真正要展示的字段。**`password` 永远不出现在出参里**，这是安全底线，不是可选项 |
| `404`             | 数据库里没有这个 id，是"资源不存在"，不是参数格式错（参数格式错才是 400）          |

## 第 4 条 · 修改用户

- 方法：`PUT`
- 路径：`/api/users/{id}`
- 入参（path）：`id` int 必填
- 入参（body，JSON）：`name` string 必填；`age` int 必填
- 出参（data）：改完之后的完整用户对象
- 状态码：成功 `200`；参数校验失败 `400`；找不到 `404`

```json
{
  "code": 200,
  "msg": "success",
  "data": { "id": 3, "name": "Rookie", "age": 21 }
}
```

**为什么这么写：**

| 点                         | 为什么                                                          |
| ------------------------- | ------------------------------------------------------------ |
| 用 `PUT` 不用 `POST`         | PUT 是"整体替换某一条"，POST 是"新增一条"。改已有资源用 PUT                       |
| id 在 path，name/age 在 body | id 决定"改谁"（定位），name/age 是"改成什么"（内容）。定位放 URL，内容放 body          |
| 出参返回整个对象                  | 前端改完要立刻刷新页面，你把改后的最新值给它，它就不用再发一次查询                            |
| `400` 和 `404` 都可能有        | 400 = 你传的 age 是 "abc" 这种格式/校验问题；404 = id 对但这个人不存在。两个不同原因，别混用 |

> 局部改一个字段（比如只改昵称）才用 `PATCH`。整条替换用 `PUT`。W1 只需会 `PUT`。

## 第 5 条 · 删除用户

- 方法：`DELETE`
- 路径：`/api/users/{id}`
- 入参（path）：`id` int 必填
- 出参（data）：`null`
- 状态码：成功 `204`；找不到 `404`

```json
{
  "code": 204,
  "msg": "no content",
  "data": null
}
```

**为什么 204 不写 200：**

200 的意思是"我处理成功了，而且**有东西返回给你**"；204 的意思是"处理成功了，但**确实没内容可返回**"。删掉之后数据库里已经没有这条记录了，返回数据是空的，所以 204 更准确。

**⚠️ 这里有个真实的冲突，必须知道：**

按 HTTP 规范，`204` 的响应**不能带响应体**。而我们的统一格式 `code/msg/data` 本身就是一个响应体。所以工程上有两种做法：

- **A（严格守规范）**：返回真正的 204，body 为空，前端只看状态码。
- **B（守统一响应体）**：返回 200，`data` 为 `null`，前端只看 `code`。

你在 W1 的模板里要求"每条都有 code/msg/data"，那实际项目里多数走 B；面试被问到时，能说出这个取舍，比死记一个数字更值分。上面 JSON 我按 A 的语义写给你看，但**你自己项目里实现时建议走 B（200 + data: null）**，理由是前端统一拦截器只认 `code`，混着 204 会让拦截器多一个分支。

## 第 6 条 · 用户登录

- 方法：`POST`
- 路径：`/api/auth/login`
- 入参（body，JSON）：`username` string 必填；`password` string 必填
- 出参（data）：`token` string
- 状态码：成功 `200`；参数缺失 `400`；用户名或密码错 `401`

```json
{
  "code": 200,
  "msg": "success",
  "data": { "token": "eyJhbGciOiJIUzI1NiJ9.xxx.yyy" }
}
```

**为什么这么写（这里有两个你昨天做错的点）：**

| 点                        | 为什么                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| 用 `POST`                 | 登录是"提交凭证、创建一次会话"，不是查询，也不是改某条资源                                                           |
| 凭证放 body 不放 URL          | 放 URL（query）会被浏览器历史、Nginx 日志、代理服务器全部记下来，密码等于明文泄露                                         |
| 密码错 = `401`，**不是 400**   | 400 是"你请求的格式/参数不合法"（比如没传 password 字段）；401 是"你给的身份凭证不对"。密码错属于后者                           |
| 用户不存在也回 `401`，**不回 404** | 如果"用户不存在"回 404、"密码错"回 401，攻击者就能挨个试用户名，靠状态码差异判断哪些账号存在（用户枚举攻击）。统一回 401 + "用户名或密码错误"，才不泄露信息 |
| 出参只给 token               | 前端拿到 token 存起来，后续请求放 `Authorization` 头里。**不要把用户信息一起塞进入参/出参**，那是 `GET /api/users/{id}` 的事 |

> 严格 REST 派会把这个接口写成 `POST /api/tokens` 或 `POST /api/auth/sessions`（把"令牌/会话"当资源）。用 `/api/auth/login` 是业界最常见的写法，两者都能接受，但你要知道 `/login` 里那个 login 其实是动词。

## 口述自测（遮住上面再答，卡住就说明没懂）

1. `/api/users/{id}` 里的 `{id}` 为什么不算"路径里的动词"？
2. 为什么"查不到用户"是 404，而"age 传了 abc"是 400？
3. 密码输错返回 401 而不是 400，这两者的分界线到底在哪？
4. 删除成功为什么 204 比 200 更准确？如果项目要统一 `code/msg/data` 怎么妥协？
5. 登录的密码为什么绝不能放在 URL 里？

**答案要点（先自己答，再对照）：**

1. `{id}` 是名词"用户"的定位标识，不是动作；动作由 GET/POST/PUT/DELETE 表达。
2. 404 = 请求本身没问题，但目标资源不存在；400 = 请求本身不合法（格式/校验失败）。
3. 400 管"你发的请求格式对不对"，401 管"你的身份凭证对不对"。网关层就能拦 400，401 要查完用户/密码才知道。
4. 204 语义是"成功且无内容"；统一响应体与 204 规范冲突时，工程上常退化为 200 + `data: null`，让前端拦截器只认一个分支。
5. URL 会进浏览器历史、访问日志、代理缓存，密码明文留痕；body 不会。
